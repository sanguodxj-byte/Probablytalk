# 上下文不设上限

送入模型的上下文一律全量下发，禁止任何形式的容量上限：字符/字节/token 预算、分区条数上限、
字段文本截断、历史轮数丢弃。原先的 `MaxContextChars = 4500` 预算裁剪、柜台 12/橱窗 8/带货 10/
事件 4/近句 3 的条数闸门、事件说明 160 字与原版台词 400 字截断、24 轮历史上限、
summary/stance/memory 的 400/120/200 字硬砍，全部删除。

**Why:** 上限是静默失真——被砍掉的那件货、那句台词，模型不知道自己没看到，于是编造或泛泛而谈，
而日志里一切正常。玩家侧代价（请求变大、回包变慢）是可观测的，用调试面板的 token 消耗暴露出来，
由人判断；而静默裁剪造成的错误无法事后发现。长度口径另有两条理由：
一是 `PromptBook` 与离店总结提示词已经写明「一到两句」「两三句话」，代码再砍同一句话就是两层复写、
自相矛盾；二是本模组既有的护栏原则——不做硬挡，需要约束就交给提示词或玩家可配置项。

**How to apply:**
- 新增上下文分区时只加事实，不加「够模型点题即可」这类截断判断；怕膨胀就报 token，不是砍内容。
- 多轮对话的往来记录只走一条传输通道：柜台交互作为 `messages` 逐条发出，上下文里不再复制一份；
  离店总结没有 `messages` 通道，转录全文随上下文下发。二者由调用方选定，`StoreContext` 不猜。
- 长度要求写在提示词里，写在代码里的只有玩家可配置项。

## 豁免（这些不是上下文上限，保留）

| 项 | 位置 | 为什么保留 |
|---|---|---|
| 议价幅度/轮次/赊账额度 | `BargainBridge` `CreditBook` | 游戏数值规则，是要下发给模型遵守的事实，不是容量闸门 |
| 每日请求数 / 单句长度 / 超时 | `SpeechSettings` `ClientSpeech` | 玩家可配置项；单句长度约束的是发言成品，不是上下文。注意连带效果：顾客那句话成形时已被裁短，随后进 `messages` 历史的就是裁短后的本体——这是说话规矩在起作用，不是历史被砍 |
| 同时在店常客数 / 每日沉淀数 | `RegularManager` | 游戏模拟规模，不是请求内容 |
| 调试日志环形 100 条 | `ApiLogTracker` | 界面历史列表的内存回收，不进请求；累计 token 计数不受它影响 |
| 顾客档案 300 条 | `CustomerArchive.MaxRecords` | 存档体积；删的是整条离线档案记录，不是单次请求的内容 |
| 名册摘要 180 字 / 12 行 | `CustomerRosterUI` | 游戏界面显示裁剪 |
| 并发 2 / 重试 3 / 各类超时 | `Player2Client` `Player2Auth` | 传输护栏，饱和即失败而非排队 |

## 机器检查

`python tools/check_context_limits.py`——扫上下文通路 10 个源文件，检出四类违规模式：
体积预算（`max_tokens` / `*Max*Chars` 一类命名）、定长截断、条数封顶（命名常量与 `Count` 数值比较）、
历史丢弃（`RemoveAt(0)` / `Skip` / `Take`）。另有引用面守卫：任何调用 `StoreContext.Build`、
`ContextBrief.Render`、`Chat(...)` 的文件都必须先进检查清单，否则新增一条上下文通路会悄悄逃过检查。

检查器自带双向合成夹具，每次运行都先自测：脏样例四类逐一必须被抓，干净样例（空判、按键名切分、
注释里提到旧常量名）一律必须零报，夹具不过直接退出码 2 而不是报绿。豁免写在脚本顶部 `EXEMPT` 表里，
每条必须带理由，表本身就是审计面。
